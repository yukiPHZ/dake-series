# DakePDF差し込み 検証記録

検証日: 2026-10-18。Windows 11、Python 3.12.4、PyInstaller 6.19.0。
正式配布は引き続き onefile。公開・commit・push は実施していない。

## 調査結果

作業開始時、正式フォルダには build、dist、spec、pycache だけが残り、ソースと正本が欠落していた。
前回作業領域の修正版 main.py と、正式フォルダに残る Python 3.12 のコードオブジェクトが一致することを確認した。
この修正版と既存ステージングの正本・派生文書・依存定義・build・gitignore を復元してから修正した。新規実装への置換ではない。

前回の修正版に存在した対策:

- root だけに限定した Configure 処理とフッターモードの変更判定。
- 160ms debounce、ロードID、リサイズ要求ID。
- メインスレッドでの PhotoImage 生成。
- 一部 after の終了時取消。

今回確認した問題:

- 起動時に fitz、Pillow、pypdf をすべて import していた。
- 全ページ分の Tk ウィジェットを同期生成し、全ページ分の PIL / PhotoImage を保持していた。
- リサイズ要求ごとに全画像を処理する新しい thread を作っていた。世代不一致でも worker 自体は処理を続けた。
- queue を空になるまで無制限に処理していた。
- ドロップ複数ファイルの先頭だけを黙って採用していた。カード内子要素への登録も不足していた。
- PDF保存を完成ファイルへ直接書いていた。

300ページ試験で GUI heartbeat が最大1.131秒止まる状態を再現した。
今回の環境でプロセスの自然終了クラッシュは再現していない。過去のクラッシュの全原因を断定するものではない。

## 実装

- 軽い画面を先に表示。PDFエンジンは初回PDF追加時、pypdfは保存時、ImageTkは最初の画像反映時に遅延 import。
- PDF解析・基準画像生成・PILリサイズは、Tk参照を持たない専用worker 1本に直列化。
- 表示範囲を最優先、前後2ページを先読み。画面外カードのTkウィジェットは作らない。
- PILキャッシュは48ページかつ24MiB以下。PhotoImageは現在範囲と先読み分だけ保持。
- 120ms debounce。待機要求を置換し、load ID / request ID 不一致の結果を破棄。
- queueは最大32件。メインスレッドのpollは1回8msを上限とする。
- PhotoImageはmain threadだけで生成し、Canvasの既存画像を置換。サイズ変更中も旧画像を保持する。
- サイズ変更時は左端の論理ページ位置を維持。ホイールはサムネイルCanvas内だけで処理し、小さいdeltaも累積。
- 両PDFカードとラベル・ボタンを明示的なドロップ対象にした。複数ファイルは説明付きエラー。
- 操作ボタン、保存先、状態表示を別行に整理。フッターは両ブロックの実要求幅で左右/中央2段を切り替える。
- 保存は同一フォルダの一時ファイルに書き、再読込でページ数を確認してからWindows renameで公開。既存出力へ上書きしない。
- 終了時は描画要求・afterを無効化。保存workerはキャンセルを確認し、一時ファイルを除去してから終了。
- 通常時に性能ログを出さない。開発時だけ DAKE_INSERT_PROFILE / DAKE_INSERT_PROBE を指定できる。
- onefileを維持し、不要なcollect-allと数値計算・可視化等のオプション依存をbuildから除外。

## 測定方法

perf_counterによる計測。4 / 20 / 100 / 300ページを各3回、新しいPythonプロセスで測定。
同じA4縦、ページラベル、24行のテキストと枠線を持つPDFを使用した。
ページ数表示時間は解析単体ではなく、追加受付からUIに反映されるまでを含む。
beforeは既存コードのPhotoImage生成とUI状態を観測、afterは開発時のみの測定値を利用した。
初期準備完了はbeforeの全ページ完了、afterの表示範囲完了という製品上の準備条件を比較する。
サイズ確定は最後の210px要求から、現在範囲がその画像サイズで反映されるまで。高速10往復を送信した。
メモリはWin32 GetProcessMemoryInfoのWorkingSetを20ms間隔で採取した試験中最大値の中央値。

### exe起動

外部プロセスの起動から、該当exeの可視ウィンドウを初めて観測するまでを測定。
別exeや他の試験ウィンドウはプロセスの実行ファイルパスで除外した。
各4回。1回目を本セッション初回、2〜4回目を連続起動として扱う。
OS再起動やファイルキャッシュ消去は行っていないため、厳密なコールド起動とは呼ばない。

|版|初回表示|連続起動3回|連続起動中央値|
|---|---:|---|---:|
|before onefile|2.295|1.884 / 2.088 / 2.032|2.032|
|after onefile|2.809|1.634 / 1.598 / 1.442|1.598|
|比較用 after onedir|0.755|0.259 / 0.269 / 0.263|0.263|

onefile連続起動は約21%短縮した。一方、本セッション初回は遅くなっており、初回改善は主張しない。
after onefileの起動からmain entryまでは初回2.559秒、連続1.382 / 1.349 / 1.248秒。
これは展開とPython起動を含む時間であり、展開だけの厳密な分離値ではない。
afterのMapからidle処理までは約0.002秒、外部からの応答確認は初回表示後約0.05秒以内だった。
onedirは展開が不要なのでさらに速いが、フォルダ一式の配布・同梱物維持が必要になる。正式配布方式は変更していない。
正式exeのサイズは51,210,154 bytesから約40.6MBへ縮小した。

## 機能・GUI検証

- 自動テスト: 10件成功。先頭・途中・末尾の順序、入力SHA-256不変、保存失敗、保存中キャンセル、既存ファイル非破壊、結果キュー満杯時のworker終了を検証。
- 300ページGUI: 高速10往復、連続スクロール、サイズ確定、左端ページ維持、差し替え、stale result無視、処理中終了を検証。
- 離れた複数の範囲へスクロールした場合もPILキャッシュ最大23.64MiB。初期画像は6枚、PhotoImageは現在範囲だけ。
- 最終10件実行時のGUI試験の最大heartbeat間隔は0.128秒。Tk PhotoImage生成スレッドを実行時assertで検査。
- 1062x740クライアント領域（外枠込み約1062x772相当）、920x680、1400x900を自動検証。
- Tkのフォント倍率100 / 125 / 150%相当でも1062x740でボタン・フッターが領域内に収まることを検証。実OSの倍率変更試験ではない。
- 実onefile GUI: 30秒放置、300ページ/2ページ読込、マウスによるスライダー拡大縮小、ホイール横スクロール、閲覧位置維持、位置変更、保存、4ページへの差し替え、最大化/復帰、通常終了を確認。
- 実exeから5ページ目の後へ保存した302ページPDFを再読込し、SRC1〜SRC5、INS1、INS2、SRC6〜SRC300の全順序一致を確認。
- 最終exeでも4ページ＋2ページを2ページ目の後へ保存し、SRC1、SRC2、INS1、INS2、SRC3、SRC4の一致を確認。Pythonの通常コンソール起動・通常終了も例外なし。
- UI_TEXT検査成功。共通アイコンの参照とbuild埋め込み、ウィンドウタイトルバー表示を確認。
- フッター全文、区切り非リンク、コピーライト非リンク、2箇所だけのリンク実装を確認。

- トラックパッド固有の水平イベント、実Windows 125% / 150%、厳密なコールド起動、Explorer/タスクバーのアイコンキャッシュは未確認。
