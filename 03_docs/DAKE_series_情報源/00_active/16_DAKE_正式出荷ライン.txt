## 基本定義

DAKEシリーズでは、GitHub Release公開だけでは正式出荷完了としない。

正式出荷とは、正本から派生ビューが生成または整合され、必要な出荷先へ届いている状態である。

## SNS投稿と予約設定（v2補足）

通常出荷ではSNS予約を行わず、Buffer下書き作成までを標準とする。

通常出荷のSNS工程は、媒体別投稿文生成、指定媒体のBuffer下書き作成、終了とする。
この工程では即時公開、予約公開、Queue投入を行わない。

予約設定は、ユーザーが対象アプリ・媒体・日時を明示し、予約計画を確認した後に限り実行する。

媒体はX・Threads・Instagramから任意に選択できる。
指定がない場合はX・Threads・Instagramの3媒体を標準対象とする。

Codexは通常出荷時に即時公開または自動予約を行わない。

v2_closedは、出荷証跡とBuffer下書きが揃い、人間が投稿・予約・修正・見送りを判断できる状態を表す。
予約済み・公開済みであることはv2_closedの必須条件にしない。

## Pack Stripe release command（Phase 16C追記）

Pack商品も単品正式出荷コマンドを使用する。

```powershell
python tools\release_product.py <product_id>
```

Packでは、Stripe payload生成前に以下を必須確認する。

- Pack ZIPが存在する。
- Pack ZIPのサイズとSHA256が正本・manifestと一致する。
- 購入後配布方式が `manual_email_private_download` として正本化されている。
- `purchase_delivery_ready=yes` である。
- 配布期限、購入者向け案内、再送、不達対応、共通手動配布ルール参照がある。

購入後導線が未確定のPackは、Stripe決済を開かない。

Pack ZIPや非公開配布URLをpublic repo、generated JSON、Store静的ファイルへ置かない。

Payment Link作成後は、確定したPayment Link URLだけを別工程で `ORIGINAL.md` へ書き戻す。
# Product release pipeline (Phase 17A)

正式出荷は商品ID単位のpipelineで現在地を判定する。

入口:

```powershell
python tools\release_product_pipeline.py <product_id>
python tools\release_product_pipeline.py <product_id> next
python tools\release_product_pipeline.py <product_id> advance
```

pipelineは `01_apps/**/ORIGINAL.md` と `04_packs/**/ORIGINAL.md` を直接探索し、generated JSONを正本探索の必須条件にしない。

一度の `advance` で進める工程は1つだけとする。Stripe live実行、Checkout確認、Store同期、本番確認など、人間確認が必要な地点では必ず停止する。

Packは例外商品ではなく、appと並ぶ主力商品種別として同じpipelineに載せる。Pack追加時にpipelineコードへPack IDや価格、ZIP名をハードコードしない。

既存Stripe対応済みアプリは、現在の証跡方式導入前の商品として `LEGACY_COMPLETE` で扱える。過去商品のstate/result/checkout証跡を捏造して補完しない。

pipelineはSecretを読まず、Stripe APIを呼ばず、Git commit/pushやStore本番反映を自動実行しない。外部作成、Checkout確認、正本確定、Store公開の境界を維持する。

Phase 17B-1では、新規PackがBOOTH登録素材まで揃った状態を `BOOTH_REGISTRATION_PENDING` として扱う。

このstageではPack正本、Pack ZIP、manifest、README、注意事項、booth_product、BOOTHサムネイルが揃っているが、BOOTH URLとStripe Payment Linkは未設定である。

BOOTH登録は自動実行しない。登録後は以下のコマンドでBOOTH URLを正本へ記録する。

```powershell
python tools\record_booth_registration.py <product_id> --booth-url <BOOTH商品URL>
python tools\record_booth_registration.py <product_id> --booth-url <BOOTH商品URL> --apply --confirm-product-id <product_id> --confirmation-text "RECORD BOOTH REGISTRATION <product_id>"
```

このコマンドはBOOTH APIを呼ばず、URL検証と `ORIGINAL.md` の最小更新だけを行う。Stripe情報は変更しない。

# Phase 18 commerce/social closeout

`RELEASE_COMPLETE` means commerce completion: Stripe, source finalization, Store generation/sync, and production review are complete.

Formal release v2 is a separate layer:

```text
commerce_status=complete
social_status=buffer_drafts_complete
formal_release_status=v2_closed
```

If commerce is complete but Buffer drafts are missing:

```text
social_status=buffer_drafts_pending
formal_release_status=v2_pending
next_formal_action=create Buffer drafts
```

Normal social release creates Buffer drafts only. It does not publish, schedule, or intentionally queue posts.

Pack products are social release targets. Pack posts must link to the Store product detail page, not directly to BOOTH, Stripe, GitHub Release, or private delivery URLs.

Stripe commerce v1 supports:

```text
app_one_time
pack_one_time_manual_delivery
digital_product_one_time
web_service_one_time_manual_fulfillment
web_service_one_time_redirect
```

Stripe commerce v1 does not support:

```text
subscription
recurring price
usage based billing
automatic account provisioning
automatic entitlement
webhook fulfillment
refund automation
customer portal
```

For new Pack releases, the target high-level flow is:

```text
Pack creation and BOOTH-ready material
BOOTH registration by human
BOOTH URL record
Stripe dry-run
Stripe live execution with explicit confirmation
Checkout human review
source finalization
Store generation/sync
production review
Buffer drafts
v2_closed
```

Normal Pack release should need two major Codex requests: one before BOOTH registration, and one after BOOTH registration. Failed safety gates remain separate follow-up work.
