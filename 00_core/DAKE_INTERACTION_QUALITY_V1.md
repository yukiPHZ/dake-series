# DAKE操作品質基準 v1

## 位置づけ

この文書は、DAKEアプリの新規開発・改修・レビューで使う共通の操作品質基準である。

機能が正しく動くことに加えて、起動して、触って、結果を見て、終わるまでの一連の体験に引っかかりを作らないことを目的とする。個別アプリの `ORIGINAL.md` が製品固有の正本であり、本書はそれを置き換えない。

## 1. 基本思想

機能数ではなく、触った瞬間の品質を見る。

```text
起動して、
触って、
結果を見て、
終わる。
```

この流れに引っかかりを作らない。

DAKEの既存原則を操作品質の中心に置く。

```text
処理は止まってもいい
UIは止めるな
応答なしは敗北
```

ここで「処理は止まってもいい」とは、重い処理そのものに時間がかかることは許容するが、その間も状況確認やキャンセルなどのUI操作を可能にする、という意味である。

## 2. 起動品質

- GUI表示前に不要な処理をしない。
- Tk rootやWindowをフォント検出などのためだけに複数生成しない。
- GUI直後に不要な重いimportは、安定性を確認したうえで遅延読み込みを検討する。
- ファイル全走査、画像・PDF解析、外部コマンド実行を起動直後に同期実行しない。
- ネットワーク処理を起動待ちにしない。
- 設定ファイルは必要最小限だけ読み、読み込みと検証を軽く保つ。
- まず操作可能なウインドウを表示し、その後で実行できる準備処理は後へ送る。

遅延読み込みは目的ではない。PyInstaller、CLI、例外表示、配布exeの安定性を壊してまで採用しない。

## 3. UI応答性

ユーザー操作には、原則として0.1〜0.2秒以内に押下状態、status、進捗開始など何らかの反応を返す。

- 0.5秒以上UIが無反応になるなら設計を見直す。
- 3秒無反応は危険と扱う。
- 5秒無反応は実質敗北と扱う。

この時間は処理全体の完了時間ではなく、UI main threadが入力へ応答できない時間を指す。ファイル解析、画像変換、PDF処理、外部コマンド待機などの重い処理をmain threadで実行しない。

## 4. 差分更新原則（再描画・再生成）

DAKEでは、状態の一部しか変わっていない場合に画面全体を再生成しない。内部配列を順序・状態の正本とし、その差分だけをUIへ反映する。

```text
状態差分
↓
必要箇所だけ更新
```

並び替え、選択変更、リサイズ、ドラッグなどの軽い操作では、次を優先する。

- 並び替えは、既存WidgetやCanvas itemを保持し、影響範囲だけ再配置する。
- 選択変更は、変更前後の表示要素だけ更新する。
- リサイズは、再生成が不要なら既存itemの位置・幅を変更する。
- ドラッグ中はプレビュー状態としてmarkerだけを更新し、順序はドロップ時に1回だけ確定する。
- 重いデータ生成は軽い操作イベントから分離する。

次の処理を軽い操作ごとに繰り返さない。

- 全Widgetの `destroy` / `recreate`
- `canvas.delete("all")` からの全描画
- サムネイルやプレビューの再生成
- ファイルの再読込・再解析
- 既に不要になった重い処理の再投入

画面上の順序と、保存・変換に使用する内部データの順序は常に一致させる。全再生成が本当に必要な場合は操作中ではなく確定時に1回だけ行う。

ただし、差分更新のために状態管理や例外処理が過度に複雑になる場合は、正しさと理解しやすさを優先して単純な再構築を選んでよい。最重要判断は「速いコード」ではなく「不要な仕事をしないコード」である。

## 5. キャッシュ

同じ情報を短時間に繰り返し計算・解析しない。

対象例：

- PDFページ数
- サムネイル
- 画像プレビュー
- ファイル情報
- 重い変換結果

キャッシュキー、無効化条件、保持期間を説明できる範囲で導入する。同じファイルでも更新時刻や内容が変わるアプリでは、古い結果を誤用しない。キャッシュ管理自体が処理や理解を複雑にする場合は導入しない。

## 6. worker / threading

「1入力または1操作 = 新規thread」を無制限に繰り返す設計を避ける。

大量投入や連続操作が想定される場合は、次を検討する。

```text
Queue
+
固定worker
```

worker数はCPU処理、I/O処理、使用ライブラリ、メモリ量、キャンセル要件に応じてアプリごとに決める。固定値を全DAKEアプリへ強制しない。連続するプレビュー要求では、古い要求を破棄して最新要求だけを処理する方式も検討する。

## 7. UI threadとの責務分離

worker threadからTk Widgetを直接操作しない。

原則は次の流れとする。

```text
worker
↓
queue
↓
after
↓
UI thread
```

workerは計算・I/O・変換結果と例外情報を渡す。Widget更新、`StringVar` 更新、ダイアログ表示、画像参照の保持はUI threadで行う。終了時には `after` タイマーやworkerの停止条件を残さない。

## 8. 大量データ時の品質

「普段3件だから動く」で判断せず、対象アプリで合理的に想定できる大量入力でも次を確認する。

- UIが止まらない。
- thread数が入力件数に比例して暴走しない。
- 不要な再生成・再読込をしない。
- スクロール、選択、並び替え、キャンセルなどの操作可能状態を維持する。
- 進捗やstatusの更新頻度が高すぎて、それ自体が負荷にならない。

件数だけでなく、大きな1ファイル、連続クリック、ウインドウリサイズ、終了直前の操作も確認する。

## 9. 完了品質

DAKEでは処理速度だけでなく、「終わったことがすぐ分かる」ことも性能として扱う。

次の状態を混同しない。

- 処理中
- 保存中
- 完了
- エラー

成功時は保存先や結果を明確にし、次に必要な操作を最小にする。エラー時は何が失敗したかと、再試行に必要な情報を示す。キャンセルは可能な処理単位で確認し、長時間「キャンセル待ち」にしない。

## 10. 演出との区別

速さをごまかす演出は禁止する。

許可するもの：

- 即時の状態表示
- ドット進行など軽い待機表示
- 軽いhover
- 実処理に対応する必要な進捗

避けるもの：

- 不要なアニメーション
- フェード
- 重いtransition
- 視覚効果による疑似高速化

演出を追加する場合も、main threadの応答性と終了時のタイマー解除を優先する。

## 11. 共通化判断

良かった実装を即座に共通moduleへ移さない。最低でも複数アプリで同じ問題と同じ解決が確認できた後に共通化を検討する。

```text
2〜3アプリ以上で同じコードが必要
+
差異が小さい
+
共通化した方が理解が簡単
```

を満たすなら共通化候補とする。共通化によってライフサイクル、例外処理、ビルド依存が分かりにくくなるなら、各アプリへ小さく持つ方を選ぶ。

フォント検出、Window icon、worker queue、UI queue、遅延読み込み、キャッシュ、status animationは候補になりやすいが、共通module化を先に決めない。

## レビュー時の確認記録

改修時は、少なくとも次を記録する。

- 操作可能なウインドウが表示されるまでの起動体感または計測値
- 通常件数と合理的な大量件数での操作結果
- main threadへ残した処理と、その理由
- worker数、queue、キャンセル、終了処理
- 再描画・再読込・キャッシュの方針
- 処理中、完了、エラーの見え方
- CLI、exeビルド、既存連携への回帰確認

数値を取れない場合は、測れなかった理由と手動確認範囲を明記する。
